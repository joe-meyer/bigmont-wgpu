# Browser validation of the Fermat ladder (2026-11-25)

Page `web/fermat.html`, kernels `web/kernels/matrix/` (generated by `dump_wgsl` from commit `d8e13ac` of `phase1`, the
merged limb-factory work). Browser: the Claude desktop app's built-in pane, **Chrome 156.0.8078.100** (Tint), WebGPU
adapter reported as vendor `amd`, architecture `rdna-2` (this machine's RX 6700 XT), features include `subgroups`,
subgroup size 32 to 64, not a fallback adapter. Windows 11.

## What was tested

1. **Compile** (`getCompilationInfo()` plus `createComputePipelineAsync`) of every 13-bit Fermat-ladder kernel in the browser
   form (`enable subgroups;` and `diagnostic(off, subgroup_uniformity);` prelude): operand sizes 64, 254, 1,019 and 2,029
   bits, TPI 4, 8, 16, 32, workgroup 64 (16 kernels, 4.7 KB to 183 KB of WGSL each). **All 16: no messages, pipeline created.**
2. **Negative control**: the two native-only 32-bit kernels (`limb32_native_fermat_...` and `limb32_native_squarings_...`,
   2,029 bits, TPI 8, which use `u64`) given the same prelude. **Both rejected** by the browser's compiler with parse errors
   at the first `u64` use (for example "expected ';' for variable declaration (line 68)"). This is the real-browser
   counterpart of the naga capability test: the 32-bit scheme cannot run on the web, and the tuner/generator never
   offers it for the browser target (`try_wgsl_for(Target::Browser)` is an `Err` naming int64; `dump_wgsl --scheme 32
   ...-browser` exits 1).
3. **Correctness, end to end**: the Fermat ladder run on the GPU through the same segmented-dispatch scheme as the native
   `Runner` (host prepares `R mod n`, `2R mod n`, `-n^-1 mod 2^13`, the exponent words; dispatches of 1, 2, 4, ... iterations
   up to about 0.1 s; verdict `x mod n == R mod n`), on a mixed batch per kernel: random odd composites, probable primes
   found in the page, the all-ones number 2^bits - 1 and 2^(bits-1) + 1, a candidate count that is not a workgroup
   multiple. **Every verdict compared with a BigInt `2^(n-1) mod n == 1` oracle: all 16 kernels, 0 wrong.** Candidates per
   kernel: 192 (64 and 254 bits, 40 PRPs among them), 110 (1,019 bits, 8 PRPs), 65 (2,029 bits, 3 PRPs). Limbs were also
   checked to be below 2^13.
4. **Throughput batch**, random odd numbers, verdicts of a random sample of 16 compared with the oracle (all matched):

| bits | candidates | TPI 4 | TPI 8 | TPI 16 | TPI 32 |
|---|---|---|---|---|---|
| 64 | 16,384 | 866,878 | 819,200 | 549,799 | 451,350 |
| 254 | 16,384 | 604,576 | 510,405 | 432,296 | 412,695 |
| 1,019 | 4,096 | 75,156 | 76,992 | 61,317 | 48,704 |
| 2,029 | 4,096 | 21,103 | 24,151 | 20,877 | 17,145 |
| 2,029 | 32,768 | 29,119 | 33,581 and 34,449 (two runs) | | |

Tests per second of ladder wall time (dispatch, wait, in the page, not counting host preparation and the readback
verdict computation), workgroup 64. The 4,096-candidate 2,029-bit runs last only 0.17 to 0.24 s, so the ramp-up of the
first short dispatches is a visible part of them; the 32,768-candidate rows are the fairer figure.

## What this says

- The 13-bit Fermat kernel (the one the factory keeps for the browser) compiles and is correct in a real browser at every
  size and width tested, in Tint, on RDNA2.
- Its speed at 2,029 bits with TPI 8 (about 34 k tests/s at 32,768 candidates) is within a few percent of the native
  runner's GPU-time rate on the same card (35.3 to 35.7 k tests/s for 16 to 32 k candidates, Phase 1 report section 4.3).
  One run each, not controlled for clocks or other load, so no stronger claim than "same range".
- The 32-bit kernels cannot be generated for or run in the browser, as designed.

## Not tested

Other browsers (Firefox, Safari), other GPUs/vendors/drivers in a browser (this is one RX 6700 XT, one Chrome build, one
OS), the browser's watchdog on much longer dispatches, memory limits at large batches, mobile, the software fallback
adapter, and the 13-bit squaring-mode kernels from this commit (`index.html` last ran them in Phase 1; their arithmetic
is the same code as the ladder's, which passed here). The page takes the host-side preparation and verdict
recomputation out of the timing, unlike the native engine's end-to-end figure. Exact oracle: JS BigInt, checked at
every size on the mixed batch; the throughput batch checks a sample of 16 verdicts only.
