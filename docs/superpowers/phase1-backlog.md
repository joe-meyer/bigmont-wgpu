### Open: from the validation run
- Engine default capacity (16,384 candidates per dispatch) leaves 10% (RTX 4070) to 19% (RX 6700 XT) of GPU-time throughput on the table against 65,536; expose `--capacity` and make the default depend on the adapter (or on the autotune).
- Autotune timing is short (256 workgroups, best of 2): it reads 11% to 13% below long-dispatch sweeps on the big GPUs and misranked TPI 4 on the Radeon 780M (8.0 M against 24.3 M squarings/s at 0.35 s dispatches), so it picked a configuration about 3% slower. Lengthen or warm up the measurement and re-check the ranking at a long dispatch.
- CPU re-check of every GPU PRP: fine for sparse primes, but on PRP-dense input (Beacon's canary file, half primes) it dominates (3.8 k tests/s engine against 43.6 k raw runner on the 4070). Overlap the re-check with GPU work, re-check a sample, or add the Gerbicz-Li check on the GPU and re-check only alarms.
- Two unexplained failures. (a) RTX 4070 `Xid 32` plus "Parent device is lost" in `chain.rs::unrolled_long_chain_matches_oracle` (once, not reproduced in 6 later runs). The Xid lines are not tied to the failure by any saved timestamp, and the quoted process name is the first test of that binary, which passed, so the attribution is not established. The failing path is the Phase 0 test helper opening a new device per check (`common::open_gpu`). To settle it: save a timestamped `journalctl -k` next to each log, loop the `chain` binary 50 times, and try a variant that shares one device. (b) A crash at process exit, exit code 0xC0000409 (a fast-fail; Git Bash shows it as 127), after all tests passed: it reproduced. The desktop `engine` test binary crashed in 2 of 8 Vulkan completions (the first run and run 6 of `desktop-engine-exit-repeat.txt`, which reads "exit code 127"), and the `bigmont-core` `sizes` binary crashed once in the fix wave's workspace run (1 of 4 completions); never in the 13 recorded desktop CLI runs. No panic text, no dump. Suspect native teardown (the two missing-adapter engine tests enumerate all backends and never open a device; the `sizes` occurrence has no such test). To settle it: loop each engine test and each `sizes` test alone with `--exact` 50 times recording exit codes; enable Windows Error Reporting LocalDumps for the test executables; loop the CLI with `--adapter` (and `--backend cpu` as a control). Results doc section 3.
- Engine throughput under Dx12 (with and without dxcompiler) was not measured; Dx12 TPI 4 at wg 256 is still slow (66.5 M against 73.6 M at wg 64, 2,029 bits).
- Only 2,029 bits has end-to-end throughput; measure 1,024 bits and mixed-size files end to end.
- **Device loss and uncaptured wgpu errors panic.** Only `Err` returns from autotune, `Runner::new` and `Runner::fermat` fall back to the CPU. `Runner` submits, `write_buffer` and polls run outside error scopes and `Gpu::open` installs no device-lost or uncaptured-error handler, so a lost device or an uncaptured error aborts the run with no verdict file (the verdict write is atomic, so nothing partial is left, but there is no fallback). Install handlers, wrap the submits in error scopes, and have the engine fall back to the CPU (or exit with a distinct code) when the device is lost. Deferred from the fix wave; the code comment in `engine.rs` and results doc section 8 now state exactly what is caught.
- **Runner restarts its segment ramp for every call.** `fermat()` starts at 1 iteration per submission and at most doubles, so a call with few candidates (the 3-candidate tail of a 16,387-candidate file) takes at least 11 submit-and-wait round trips for the 2,028 iterations. Measured on the 6700 XT as 0.02 to 0.13 s of extra GPU time per tail (`results/phase1/desktop-6700xt-vulkan-tail-dispatch.txt`), which explains most of the 16 k against 131 k engine rate gap (results doc 4.3). Keep the segment size across calls (or seed it from the last call), or send tiny tails to the CPU.
- **`--capacity` flag and `max_buffer_size`.** The engine's capacity (16,384) has no CLI flag, and the capacity code clamps to the dispatch-group and storage-binding limits but not to `max_buffer_size`.
- **`--device N` counts adapters across all backends** (Vulkan, Dx12 and GL list the same GPU), so it works only while Vulkan enumerates first; redesign (for example index within a backend, or print a stable adapter list).
- **Composite sampling counter restarts on every `Engine::verdicts` call**, so a call with fewer composites than `verify_rate` samples none (the 400-candidate canary re-checks no composite; a 32,768-candidate CLI chunk samples about 7). Persist the counter across calls (or sample by hash of the candidate).
- **CLI chunk tails can run on the CPU**: a chunk or bit-length bucket below `min_gpu_batch` (64) is tested on the CPU (the 131 k runs print "gpu 131072, cpu 3"). The bucket size is the only size-based reason a bucket skips the GPU (bit length is not; see "Small bit lengths" below). A failed autotune or `Runner::new` / `Runner::fermat` `Err` also sends the bucket to the CPU, counted in `gpu_errors`.
- **Small bit lengths (done after the Phase 1 review).** The GPU is used by default down to 2-bit numbers (odd n >= 3); `Runner::new` rejects only `bits < 2`, and the old "buckets under 64 bits always run on the CPU" rule is gone. Evidence that the Fermat ladder is correct at these sizes: an exhaustive GPU test of every odd n from 3 to 4,095 (bits 2 to 12) at TPI 8 and 4, 2^k-1, 2^(k-1)+1, 2^k+1, random numbers and probable primes at 20, 26, 31, 32, 33, 39, 47, 48, 49, 52, 63, 64 and 65 bits (TPI 8 and 4), n = 3 at TPI 4, 8, 16 and 32, the existing random tests at 64 to 3,000 bits, and the engine's CPU re-check of every GPU probable prime (plus the sampled composites). It is not proven for every length between 13 and 64 bits. Autotune now tunes per limb class (`tune::limb_class`, at least 4 limbs, so 2 to 48 bits form one class) at the class's largest length `13 * limbs - 4`, and the engine tunes each class once and builds one `Runner` per exact bit length (`EngineReport::tuned_classes`). **Measured at 40 bits** (20,003 candidates, RX 6700 XT, Vulkan, 16-thread CPU; logs `results/phase1/desktop-6700xt-vulkan-40bit-gpu-vs-cpu.txt` and `desktop-6700xt-vulkan-tune-40.txt`): the GPU is slower than the CPU. Warm-cache engine runs print 1.0 to 1.4 M tests/s "excluding tuning", but that subtracts the 0.03 to 0.04 s of cache-hit self-test and Runner build from runs of 0.04 to 0.06 s, so end to end it is about 0.35 to 0.5 M tests/s (the one first run in the saved log took 3.48 s in total, 3.40 s of it tuning); the CPU does 4.3 to 4.6 M tests/s (about 4.4 ms). So the GPU is about 4x slower on the figure that leaves out setup and about 10x slower end to end. The padding is not the cause: the tuner chose the narrowest kernel (TPI 4, wg 256, 4 limbs = 52 bits for 40-bit numbers; all 12 configurations passed the self-test and ranked by width, 9.3 G squarings/s at TPI 4 down to 0.2 G at TPI 32), and forcing 4 of the 12 configurations end to end (single runs, about +-30%; a local throwaway patch whose source was not saved, so not reproducible, see the log) gave 1.0 to 1.4 M tests/s for TPI 4 and 8 (the tuner's pick, TPI 4 wg 256, is at or near the best of those) and 0.68 M for TPI 32 (about 2x slower than the best); TPI 16 and the other workgroup sizes were not forced. The kernel arithmetic for the whole file would take about 0.1 ms at 9 G squarings/s; a direct `Runner::fermat` timing (throwaway example, source in the log) shows 14.0 to 26.0 ms per 20,003 candidates, split as: 5.7 to 13.1 ms `stats.gpu_secs` (all submit-and-wait time, about 6 ms for TPI 4 wg 64 and about 12 ms for TPI 32, so it does depend somewhat on kernel width), 3.9 to 7.6 ms host preparation (`R mod n`, packing), 4.1 to 8.9 ms other per-call work (uploads, readback, unpacking, the `x mod n` verdict compare), then 1.2 to 1.6 ms for the CPU re-check of 1,480 PRPs. That the `gpu_secs` part is mostly submit-and-wait latency of the segmented ladder (the segment ramp starts at 1 iteration per submission and at most doubles) is an inference, supported by the 0.1 ms arithmetic estimate and the earlier tail-dispatch measurement (`results/phase1/desktop-6700xt-vulkan-tail-dispatch.txt`); no submission count was logged and `gpu_secs` also contains GPU execution time. The host-side parts (prep and other) are the same for every kernel width, so for tiny numbers the CPU wins on overhead, not on arithmetic. Open: pick the CPU for classes where it measures faster (an `Auto` heuristic or an autotune that compares against the CPU rate), and cut the per-call costs listed above (segment ramp, host prep on the GPU, fewer round trips); not done here. Where the break-even size is was not measured (only 40 bits).
- **`Options::threads` is not used for the Runner's host-side preparation** (it uses all available cores).
- ~~**Fermat mode with one limb per lane has no direct test**~~ Done: the small-bits tests in `bigmont-core/tests/fermat.rs` run the Fermat ladder with one limb per lane (tpi 8 with 8 limbs and tpi 4 with 4 limbs at every length from 2 to 12 bits (exhaustive) and at 20, 26, 31, 32, 33, 39, 47 and 48 bits, and the 2-bit n = 3 at tpi 4, 8, 16 and 32).
