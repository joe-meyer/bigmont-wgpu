# What the missing carry and widening-multiply primitives cost in WGSL (2026-11-27)

Refs #3 (and #1). Tool: `crates/bigmont-core/examples/carry_bench.rs`, kernels from
`crates/bigmont-core/examples/carry_kernels/mod.rs`, checks in `crates/bigmont-core/tests/carry_emulation.rs`.

## Question

WGSL (trunk of gpuweb/gpuweb as of 2026-11-26) has no add-with-carry, no extended multiply and no
64-bit integer type. Our 32-bit-limb scheme works around that with `u64` arithmetic, which is wgpu's
native-only `SHADER_INT64` and does not exist in a browser. The only way to write a 32-bit-limb
kernel that is valid on the web is to rebuild the carries and the high word of every product from
`u32` operations. How much does that cost, on the hardware we have?

## Method

One thread multiplies (or Montgomery-multiplies, CIOS, no final subtraction) two `n`-limb numbers
and repeats it with the result fed back, so nothing can be hoisted. Two forms of the one primitive
that everything is built from, `x * y + t + c` as a (low, high) pair, compute the same bits:

- **u64**: `u64(x) * u64(y) + u64(t) + u64(c)`; native only (`SHADER_INT64`).
- **u32 emulation**: four 16x16 products for the high word, the wrapping `x * y` for the low word,
  and each carry found by comparing a sum with an operand. Valid WGSL everywhere.

Before any timing, every kernel is checked against exact big-integer arithmetic on the CPU (edge
cases first: all ones, zero, one, `n - 1`, the all-ones modulus; then random operands). A kernel that
fails prints no rate. Rates use the slope method of `scheme_compare` (dispatch of 2 repetitions per
thread, then doubled until one dispatch takes about 0.25 s, rate = threads x (R_long - 2) /
(t_long - t_short)), 65,536 threads, workgroup 64, best of 3 for the short run. "G mac/s" counts one
`x * y + t + c` step as one unit (n^2 per product, 2 n^2 per Montgomery multiplication).

```
BIGMONT_ADAPTER=<substring> BIGMONT_BACKEND=Vulkan cargo run --release -p bigmont-core --example carry_bench
cargo test -p bigmont-core --test carry_emulation -- --test-threads=1
```

## Results

Ratio = time per operation of the u32 emulation divided by the u64 form on the same device (above 1
is slower). Rates in G mac/s as `u64 / u32 emulation`.

| | RTX 4070 Laptop (Vulkan) | RX 6700 XT (Vulkan) | RX 6700 XT (DX12, DXC) | Radeon 780M (Vulkan) |
|---|---|---|---|---|
| multiply 256 bit | 1392 / 484 = **2.88x** | 546 / 230 = **2.37x** | 548 / 225 = **2.44x** | 166 / 90 = **1.85x** |
| multiply 512 bit | 1529 / 463 = **3.30x** | 533 / 220 = **2.42x** | 540 / 224 = **2.41x** | 166 / 91 = **1.83x** |
| multiply 1024 bit | 1535 / 203 = **7.56x** | 486 / 214 = **2.27x** | 517 / 219 = **2.36x** | 165 / 87 = **1.90x** |
| Montgomery 256 bit | 1507 / 425 = **3.54x** | 527 / 226 = **2.33x** | 518 / 219 = **2.37x** | 166 / 88 = **1.88x** |
| Montgomery 512 bit | 1483 / 285 = **5.20x** | 527 / 216 = **2.44x** | 524 / 211 = **2.49x** | 166 / 88 = **1.89x** |
| Montgomery 1024 bit | 1508 / 204 = **7.38x** | 483 / 211 = **2.29x** | 512 / 210 = **2.44x** | 168 / 78 = **2.17x** |

Setups: RTX 4070 Laptop, NVIDIA 580.178.04, Ubuntu 26.04, Vulkan. RX 6700 XT, Windows 11, driver
32.0.21045.16010, Vulkan and DX12 (DXC is needed for `SHADER_INT64` on DX12). Radeon 780M, Mesa
26.0.8 (RADV), Ubuntu 26.04, Vulkan. wgpu is the repo's pinned trunk commit. The RTX 4070 was run
twice; the second run agrees with the first to within 2% at every size (ratios 2.86 to 7.70). The
RX 6700 XT's Vulkan and DX12 runs agree to within 4%. Everything else is a single run.

**In a browser** (the u32 emulation only, since the u64 form cannot exist there): the same WGSL
generated by the example, run through a small throwaway WebGPU page in Chromium 156.0.8078.100
(Windows 11, on the RX 6700 XT, adapter reported as vendor amd / rdna-2) passes the BigInt check and
runs at 225 / 222 / 219 G mac/s for the 256 / 512 / 1024-bit products and 218 / 211 G mac/s for the
256 / 512-bit Montgomery multiplications, within about 4% of the same card's native Vulkan
emulation row above. The 1024-bit Montgomery kernel did **not** run in the browser: the device was
lost ("A valid external Instance reference no longer exists", reason unknown) on both attempts. The
same kernel compiles and runs natively on Vulkan and DX12. We did not look into why. The page is not
part of this change.

**Static count** (`emulation_needs_many_more_operations`, on naga's IR, no GPU): one `mac` is 1
multiply + 3 other arithmetic operations in the u64 form, and 5 multiplies + 21 other operations +
2 selects in the u32 emulation. Width conversions (`u64(x)`, `u32(p)`) are not counted: they are
register moves.

## What it shows

- Rebuilding carries and the high word from `u32` operations is slower than the `u64` form on every
  device and size measured: 1.8x to 2.5x at every size on the Radeon 780M and the RX 6700 XT, and
  2.9x to 7.7x on the RTX 4070.
- On the RTX 4070 the gap grows with size, to 7.4x to 7.7x at 1,024 bits. We do not know why (it
  looks like a cliff in the emulation's rate, 463 to 203 G mac/s from 512 to 1024 bits, while the
  u64 form stays at about 1,500). Register pressure is the first suspect; we did not check.
- The emulation is correct (bit-exact with exact arithmetic on four adapters, including a software
  one) and it runs in a browser, so a web-valid 32-bit scheme exists. It is just slow, so this is
  an argument for the missing primitives, not for the emulation being unusable.

## What it does not show

- **Not the engine's speed.** One thread per number, no subgroup cooperation, nothing like the
  cooperative kernels in `limb32.rs`. It measures the cost of the primitive, and what a 32-bit
  scheme on the web would pay if the engine's inner loop were rewritten with it. We did not do that
  rewrite, and the 13-bit scheme (which needs neither) remains the web path.
- **The u64 form stands in for a native extended multiply; it is not one.** WGSL cannot express
  `OpUMulExtended` / `OpIAddCarry` (or MSL's `mulhi`) at all, so the real ceiling is not measured.
  The 2.4x to 7.7x here is the gap to what the compiler makes of `u64` arithmetic, which on NVIDIA
  and AMD is a hardware multiply-add with a wide result; it may differ from the gap to a dedicated
  extended-multiply instruction.
- **One emulation.** Ours is the straightforward one. A cleverer one (fewer partial products, or
  deferring carries so fewer comparisons are needed) might narrow the gap. We have not tried.
- **Vendors not tested:** Intel, Apple, and every driver other than the three above. Metal in
  particular lacks 64-bit integer math on some hardware (see below), so the u64 form may not even
  run there.
- Single runs except where stated; no profiler counters or disassembly (this does not answer the
  "what do the compilers emit" half of #3).

## Why the web has no 64-bit integers (what we found, and what we did not)

Read from gpuweb/gpuweb at `a07208d` (2026-11-26) and its issues:

- The spec says "WGSL does not have a concrete 64-bit integer type", and
  `proposals/atomic-64-min-max.md` says there are "no near term plans" for one. The only 64-bit
  thing in WGSL is `atomic<vec2<u32>>` for min/max, a surrogate that avoids the type.
- [gpuweb#273](https://github.com/gpuweb/gpuweb/issues/273) (integer widths other than 32) has been
  open since 2019: "For MVP we decided to use only 32-bit integers. After MVP, reconsider". In
  September 2026 a WGSL contributor wrote that what is needed first is an investigation into which
  backend platforms support which widths and through which extensions, then a proposal, then a CTS
  and implementations, before the spec can change. No such investigation is linked.
- Hardware reach: in [gpuweb#5152](https://github.com/gpuweb/gpuweb/issues/5152) a commenter
  notes that 64-bit integer math is not supported by the Mac2 Metal feature sets. wgpu's own
  `SHADER_INT64` is documented as supported on Vulkan, on DX12 only with DXC, and on Metal with
  MSL 2.3 or later, and is native only.
- For carries and extended multiplies specifically,
  [gpuweb#1565](https://github.com/gpuweb/gpuweb/issues/1565) has been open since 2021 and was
  marked post-V1 in January 2022. The minutes record the blocker at the time: SPIR-V
  (`OpIAddCarry`, `OpUMulExtended`) and MSL (`mulhi`) have these, DXIL has a high multiply, but HLSL
  did not, and the group said it would only add what HLSL supports. ANGLE already polyfills them.

We did not find a statement of a technical reason that rules 64-bit integers out: what we found is
an unscheduled post-MVP item with a stated investigation that has not been done, plus an optional
hardware feature that WebGPU's baseline-portability model would have to expose as a feature flag
(as it does for `shader-f16`). That last part is our reading, not a quote.

## What a proposal would need (not filed)

Per #3, any outreach is the maintainers' decision and nothing has been sent. Material for one: the
primitive in question is `(lo, hi) = x * y + t + c` and `(sum, carry) = x + y` on `u32`, whose
building blocks exist as built-in operations in SPIR-V (`OpIAddCarry`, `OpUMulExtended`), MSL
(`mulhi`) and GLSL (`uaddCarry`, `umulExtended`), and which we can only emulate in WGSL at 1.8x to
7.7x the cost; the measurements above; and the test file, which is a
conformance-style check that an implementation's results equal exact arithmetic on edge cases.
